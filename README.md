# ac-launcher —— AgileCampus 独立部署启动器

在**仓库之外**运行的部署控制台。可以在任意文件夹监视任意一个 AgileCampus 检出，
维护多个项目的列表，**不改动源项目的任何一个字节**。

---

## 两条命令，两种形态

| | folder 模式 | 单文件模式 |
|---|---|---|
| 入口 | `start.cmd` / `node main.mjs` | `dist\ac-launcher.exe` |
| 需要 Node.js | 是（≥ 20，缺失时 `start.cmd` 会自动下载便携版） | 否，exe 自带 |
| 用途 | 实时开发：改动重跑、立刻看到 | 便携：任何机器上双击即可 |

**两种形态跑相同代码。** exe 只是把源码原样内嵌，启动时释放到
`<运行目录>\engine\<内容哈希>\` 再 `import()` 。所以 folder 模式是 exe 的实时预览，
排查问题时可以先用 `node main.mjs` 复现，不必重新打包。释放出来的旧版本目录
**会被自动清理**（见「engine 目录」一节）。

### 用法

```
ac-launcher.exe                      打开中枢：管理并监视所有已登记的项目
ac-launcher.exe <仓库目录>           为该仓库打开控制面板（也可以直接把文件夹拖上来）
ac-launcher.exe --repo <路径>        同上，显式指定
```

选项：

| 选项 | 说明 |
|---|---|
| `--repo <路径>` | 项目仓库目录（**只读**，不写入） |
| `--runtime-dir <路径>` | 运行目录，默认 `%LOCALAPPDATA%\AgileCampus` |
| `--node <路径>` | 指定 npm / 构建 / 启动用的 Node（默认自动查找） |
| `--port <n>` | 中枢端口，默认 8788，被占用时自动顺延 |
| `--no-open` | 不自动打开浏览器 |
| `--selftest` | 打印解析结果后退出，排查环境问题用 |
| `--help` / `--version` | |

> 在仓库目录里直接跑 exe 得到的是**中枢**，不是该仓库的面板。面板模式一律要显式
> `--repo`（或拖拽文件夹）。这是刻意的：中枢会把你登记的每一个项目都列出来，
> 包括当前这个，从那里点开就是面板；反过来若按 cwd 猜，「面板没有任何入口回到中枢」

## 三条特性

### 特性 1：源仓库零改动

面板对仓库**只读**。同步源码做的是「读仓库 → 写运行目录」，构建、启动、数据库
全部发生在运行目录内：

```bat
rem 先存基线
node verify-repo.mjs --repo "C:\...\agilecampus-master" --include-deploy save before.txt
rem ……随便怎么用……
node verify-repo.mjs --repo "C:\...\agilecampus-master" --include-deploy diff before.txt
rem 期望 exit 0
```

`--include-deploy` 不是可选装饰。默认排除项里有 `deploy/`，而在旧布局里启动器
恰好长在仓库内部 —— 于是「仓库零改动」里**唯一有可能被我们写坏的那部分**，
正是唯一没被检查的那部分。

### 特性 2：关控制台 ≠ 停服务

面板是**控制面**，应用与数据库是被控制面。停止面板只关掉控制台窗口：

- 应用是 `detached` + 文件描述符 stdio + `unref()` 起的，面板退出它不受影响
- Postgres 由 `pg_ctl` 独立拉起
- 面板自己只持有 `panel.lock`（可自愈）和无关紧要的日志缓冲

所以「杀掉面板」与「用户直接关掉控制台窗口」等价，而那本来就是被支持的停止方式。

**停止面板的两条路**：优先用监督令牌走优雅 `shutdown()`（清锁、关 server、flush
日志流）；5 秒内没生效才降级为硬杀，且硬杀前**必须核对进程启动时间**
（`identityMatches`），否则 PID 复用会杀掉无关进程。

例外：**「重新分配端口」会显式停掉应用与数据库，再按原状态拉回来**。端口要改就得让
它们重新绑定，所以它是唯一会动被控面的中枢操作，也是这里唯一会短暂中断服务的地方。

另一条路是页面上的**「全部停止并退出面板」**，它与上面那条**不是一回事**：它先按顺序
停掉应用和数据库，再退出面板。所以那个请求**做完才回话**（正常 10–20 秒，库慢时更久），
响应里带的是 `{stoppedApp, stoppedDb, errors[]}` 这组**真实结果**——从前它抢先回一句
「已受理」就撒手，而面板一消失页面就再也拿不到任何信息了。页面那边等的是同一个东西：
不拿到结果、不探到面板不再应答，它就不说「已退出」（见「已知限制」）。中间那段由
「正在停止…」+ 每秒一次的网站/数据库状态顶着，比一句假宣告有用。

### 特性 3：零运行时依赖

面板本身只 import Node 内置模块。它必须在 `npm ci` **之前**就能跑 —— 因为
「装依赖」正是它要替你点的那个按钮。

把它复制到一个完全没有 `node_modules` 的目录里跑 `node main.mjs`，中枢页与面板页
都必须能出来。`package.json` 里只有 `devDependencies`（postject，打包用），
运行期永不读取。

## 多项目：中枢

中枢（不带 `--repo` 时启动的那个）管理一份注册表 `<运行目录>\projects.json`，
列出每个项目的面板、应用、数据库状态，并可按需拉起某个项目的子面板。

**中枢监视 N 个项目不需要 N 个子面板进程。** 中枢要显示的一切
（`appStatus` / `pgStatus` / `standaloneReady`）都是 `(运行目录, 配置)` 的纯函数，
只有面板的 server/route 层是有状态的。所以子面板按需才拉起（`autoStartPanel: false`），
三个项目零面板运行时只有一个中枢进程。

端口在**加入项目时一次性预约**，写进该项目自己的 `config/panel.json`：

| | 候选 |
|---|---|
| 面板 | `8800` + 0..63 |
| 应用 | `3000`、`3080`、`3100`–`3199` |
| Postgres | `55432`–`55441` |

面板端口起点是 8800 而不是紧随中枢默认端口 8788 的 8789：中枢端口自身被占时会
顺延，顺延范围（8788–8799）必须与新项目的预约范围**结构上不相交**，否则一次顺延
就可能与某个项目的预约撞车。

**加完之后要改端口，只有一条路：中枢卡片上的「重新分配端口」。** 手工去改
`panel.json` 仍然是错的——那是制造一类已知故障：`portableDsn()` 从 `pgPort` 推导
`DATABASE_URL`，事前不一起改，事后 DSN 与 `POSTGRES_PASSWORD` 就会静默失同步

「重新分配端口」把这件事变成中枢能安全执行的事务：

- 从**同一张候选表**里挑一组新端口，排除全部已预约的值（含中枢自己的）
- 先停掉在跑的应用与数据库，改完**按原状态拉回来**。这是唯一会动被控面的中枢操作
- 把 `panel.json` 的三个端口、`databaseUrl`、`.env` 的 `DATABASE_URL` 与
  `AGILECAMPUS_URL` **一起**改对，再重启服务
- **不碰数据**：pgdata 不与端口绑定（端口是 `pg_ctl -o "-p …"` 传的，`initdb` 里没有
  端口），也不 `ALTER ROLE` —— 密码一个字节不动
- 弹窗里那三个值是**可编辑**的。中枢先探好一组空闲端口填进去，你要指定就改；
  服务端会再校验一遍（整数、互不相同、不撞中枢与别人的预约、此刻空闲）
- 请求是**同步**的，通常 10–20 秒

提交前任何一步失败都是**磁盘零改动**，按原先那几个按钮就能回到原世界。提交后某个
服务没起来则**不回滚**（端口组本身已经自洽，而用户点它的动机常常正是旧端口有问题），
改为如实汇报到操作反馈里。

**面板里原本还有两个能改端口的地方，被中枢管着时已经收口**（`AC_HUB=1` 时）：
`opStart` 遇到端口被占不再自己顺延——它会从一张硬编码候选表里挑，**完全不知道别的
项目预约了什么**，可能抢走别人的端口——改为报错并指回中枢；设置页改端口会得到 400，
不再直接落盘。独立运行面板（`--repo`，没有中枢）时两处行为与从前一致。

项目的 `panel.json` 是权威，`projects.json` 里的 `ports` 只是显示缓存。

### 已有的旧部署会被原地收编

`%LOCALAPPDATA%\AgileCampus` 里如果已有一套旧版单项目部署，中枢首次启动时把它
**原地**注册成一条 `legacy: true` 的项目：运行目录就是数据根本身。

**绝不搬动它** —— 几百 MB 的 `pgdata/` + `pgsql/`，而且 `databaseUrl` 里的路径与
密码都绑着那个位置。

旧版面板**从不往 `config/panel.json` 写 `repoDir`**（它的仓库是从 `deploy/` 的
文件位置推出来的），所以收编时仓库路径取自 `run/panel.lock`。收编之后面板会把
`repoDir` 补写进配置，这条线索从此是持久的。

**它可以被删除，也可以被清盘**，但清盘走的是另一条路：它的运行目录就是数据根，
`rm -rf` 整个目录等于把中枢自己（`projects.json`、`config/hub.secret`、
`run/hub.lock`、`logs/hub.log`、`engine/`）和**别的项目**一起删掉——而现场一声不响，
因为注册表正是被删掉的第一个文件。所以那一条按 `lib/registry.mjs` 的
`LEGACY_PURGE_RELS` **按名字**删：`src/`、`node/`、`pgsql/`、`pgdata/`、`tmp/`、
它自己的 `config/panel.json`、`run/` 下的状态文件、以及它自己的日志。
**数据根本身永远不删**，`hub.log` / `hub.lock` 也不在清单里（所以清单里绝不能出现
`config` / `run` / `logs` / `projects` 这种整目录名——加错一条就是删注册表，
`verify-legacypurge.mjs` 在打包门禁里守着这件事）。

两条路都要求**面板、应用、数据库都已停止**：清盘是按名字做的细活，postmaster 还占着
`pgdata` 时删到一半会失败，留下一个「看着还在、其实已经缺了几个文件」的数据目录。

「移出列表」（只摘条目、不动文件）对旧部署**另外记一笔** `ignoredRepos`，
否则下次启动 `migrateLegacy` 会当场把它收编回来——旧部署的条目**就是**那次收编，
文件还在原地而条目没了，用户看到的是「删了又自己回来了」。用「添加项目」把它加回来
即撤销那一笔。

## engine 目录：释放、认领与清理

exe 每次换一个版本，就把内嵌源码释放到 `<运行目录>\engine\<内容哈希>\`。目录名是
**内容哈希**，所以同一个 exe 重复启动是零写入的快速路径（`.ok` 是完成标记），而源码
改一个字就换一个目录。

这些目录**会被自动清理**，判据是 `boot.cjs` 里的纯函数 `planEnginePrune`：

| 目录 | 处置 |
|---|---|
| 当前版本 | 永远留 |
| `.tmp-<hash>-<pid>`，而那个 pid 还活着 | 留（别人正在释放） |
| 有 `.inuse`，而其中的 pid 还活着 | 留（有人正在用） |
| 有 `.inuse`，但 pid 已死 | 删（上次没退干净） |
| 没有 `.inuse`，且放够 7 天 | 删 |
| 没有 `.inuse`，但还没放够 7 天 | **留** |

**为什么「没人认领」也要再等 7 天。** 光看目录分不出「有进程正在用这份源码」和
「这是一份没人要的旧副本」，而 `panel.mjs` 里有一处**运行期**的
`await import('./lib/nodebin.mjs')` —— 删掉一个正在运行的进程的 engine 目录，那个
进程会当场 `ERR_MODULE_NOT_FOUND`。认领文件（`<hash>\.inuse`，内容
`{hash, pid, at}`，进程**正常退出**时自动抹掉）解决的是**新版本**；而**旧版本 exe**
释放的目录里没有这个文件，那个进程却可能此刻还在跑。7 天是「还活着的概率已经可以
忽略」的界线，而一份 engine 只有 ~400 KB —— 留着的代价远小于误删的代价。

清理**删不掉时只打印一行，绝不抛**。Windows 上删不掉通常意味着有进程正占着那几个
文件，而强行删一个正在被用的目录会毁掉那个进程；留着，下次启动会再试一遍。

已实测（交付产物层面，不是只跑函数）：在一个临时数据根里造出「死认领」「8 天无人认领」
「写它的 pid 已死的 `.tmp-*`」三个陈旧目录，跑
`dist\ac-launcher.exe --selftest --runtime-dir <那个根>` —— 三个都被清掉，刚建的无认领
目录与当次释放的那份留下，`engine\` 之外的 `projects.json` 一字未动。

## 安全

### 监听面

面板与中枢一律只绑 `127.0.0.1`。改动型请求有三重护栏：

1. **Host 必须是本机地址** —— 挡 DNS rebinding
2. **`x-ac-token` 必须匹配** —— 令牌每次启动随机生成，注入进发给浏览器的 HTML
3. **`/api/` 下的非 GET 必须 `application/json`** —— 挡掉 HTML 表单类的盲发
4. 外加 Origin 校验（只拒绝「存在且不匹配」的 Origin，服务端客户端不带 Origin）

GET 不校验令牌，这是刻意的：GET 被 Host 检查 + **不返回任何 CORS 头**保护，
跨源页面能发出请求但读不到响应。所有会改变状态的接口都是非 GET。

### 监督令牌的信任级别

中枢持有一枚监督令牌 `<运行目录>\config\hub.secret`，子面板把它记进可接受的
令牌集合，于是中枢能优雅停掉自己拉起的面板。它**落盘**是因为：若每次启动换新的，
重启中枢之后就无法优雅停掉上一轮自己起的面板，只能退化到硬杀。

这枚令牌**只走环境变量 `AC_SUPERVISOR_TOKEN`，绝不写进发给浏览器的 HTML**，
并且在两处 `{...process.env}` 之后被显式 `delete` 掉 —— 否则「部署后的站点」
和每个 `npm` / `drizzle-kit` / `next build` 子进程都会继承它。那个站点绑
`0.0.0.0`、对局域网开放，任何 dump env 的路径都会把它漏出去。

**它的信任级别与 `config/panel.json` 里明文存的 `pgPassword` 相同** ——
都是本机文件系统级别的信任。写在这里而不是留作隐含。

### exe 未签名

`dist\ac-launcher.exe` 是「复制一份 node.exe，再用 postject 把 blob 注入进去」的
产物，注入会让原有的 Authenticode 签名失效（postject 会就此告警）。

- 本机跑没问题
- **拷到别的机器可能触发 SmartScreen，也可能被杀软隔离**

这不是可以靠改代码绕开的东西，只能靠签名或加白名单。

## 与 `agilecampus-master\deploy\` 的关系

`deploy/` 是这套代码的**来源**，现在**冻结**为参考实现，一个字节都不要再改。
`ac-launcher/` 里的 `panel.mjs` / `lib/` / `ui/index.html` 都是从它复制过来的。

向后兼容因此是免费的：老路径不可能回归，因为它没被碰过。`deploy/start.cmd`
与两个验证器继续可用。

**`ui/index.html` 现在与 `deploy/ui/index.html` 不同了。** 从前这里写的是「两份逐字节
相同」，并且把它当成一条不许碰的约定。2026-09-28 打破了它，因为**只能那样修**：
页面上那句「面板已退出」是写死在 HTML 里的（点完 6 秒无条件改写整页），后端再正确也
换不掉它；而 `deploy/` 冻结、不接受改动。所以两份页面从那一刻起是**同源但已分叉**：
`ac-launcher/ui/index.html` 往前走，`deploy/ui/index.html` 停在原地，**永远不会跟上**。
这不是疏漏，是冻结的代价——写在这里，免得以后有人对着两份文件发呆。

**代价：以后修 bug 要改两处，或者承认 `deploy/` 是历史存档。采取了后者。**
下面这些修复只存在于 `ac-launcher/`，`deploy/` 里的那份仍然带着它们：

| 缺陷 | 后果 |
|---|---|
| `processStartTime` 的正则不认 JSON 转义的 `\/Date(...)\/` | **每一次调用都返回 null**，而 null 被下游当作「无法验证」放行 → 防 PID 复用误杀的保护一直形同虚设。不会报错、不会写日志，只是从不生效 |
| `rebuildAll` 用了 `proc` 却从没绑定它 | 「重新部署」每次都在**最后一步**炸成 `proc is not defined`：同步、装依赖、构建、装配全白做，界面只留下一个看不出病因的错 |
| `opStart` 遇端口被占会自己挑替代端口并落盘 | 它从一张硬编码候选表里挑，**看不见注册表**，于是可能抢走别的项目预约的端口。被中枢管着时已改为报错并指回中枢 |
| 设置页的 `appPort` / `pgPort` 无条件落盘 | 没有任何空闲与预约校验，改完 `.env` 的 `AGILECAMPUS_URL` 也留在旧端口上（它只在「没设过」时才写）。被中枢管着时已改为 400 |
| 判断「面板在不在」时把「没应答」也算成「不在」 | 面板忙着跑 npm ci 时，中枢卡片会闪「面板未打开」并谎报「锁陈旧（进程已不在）」；点「打开控制面板」会去起第二个面板，而端口被第一个占着，必然起不来。现已分成 `panelProcess` / `livePanel` 两个判据 |
| 面板写 `run/panel.lock` 是原地写、不是原子写 | 中枢每 2 秒读一次，启动那一瞬间正好读到半截 JSON 就会被当成「没有面板」。已改为 `writeJson`（tmp + rename） |
| `cmd.exe` / `reg.exe` 靠 PATH 解析 | 它们是拿来**修 PATH** 的，靠 PATH 找它们等于自举：PATH 一坏，自愈就退化成「注册表读不到」，真起 `cmd.exe` 也会变成 ENOENT，于是报出来的原因成了「找不到 cmd.exe」而不是「找不到 node」。已改为绝对路径 |
| 收编的旧部署一律不许清盘（一律 400，让你自己去资源管理器删） | 挡住是对的（整目录 `rm -rf` 会连中枢自己一起删），但没给替代方案，而**手工删恰恰最容易把 `projects.json` 一起删掉**。现在改为按名字清盘（`LEGACY_PURGE_RELS`）：删部署自己的那些文件，数据根与中枢自身不动 |
| 旧部署「移出列表」之后，下次启动会自己回来 | 它的条目**就是**那次收编，而文件还在原地，`migrateLegacy` 于是当场再收编一次。用户看到的是「删了又自己回来了」，两次之间他什么都没做。现在移除时记一笔 `ignoredRepos`，「添加项目」加回来即撤销 |
| 退出面板时喂给 `stopPortable` 的是一个**手写 job 空壳** | 它缺 `line()` 与 `flush()`，后果分两段：端口上没在监听时一进来就抛「job.line is not a function」——**数据库根本没被停**；有监听时则抛在 `spawnInto` 收尾、**在 resolve 之前**——那个 Promise 永不 settle，面板卡在 await 上**再也退不出去**。已换成真 `detachedJob`，并加了 120 秒硬超时兜底。它下面那条讲的是这件事的另一半：为什么界面会说「退了」 |
| 护栏的 `onLog` 从第一天起就在签名里、两个调用点也都传了 `log`，却**从没被调用过** | 所有被护栏拒绝的请求在日志里一个字都不留——包括那次「点了退出面板没反应」的 403，翻遍 `panel.log` 找不到任何线索。现在每次拒绝都留一行（方法、路径、原因，令牌不匹配时点明「页面可能是上一个面板进程留下的」），且**绝不写令牌值** |
| engine 目录只写不删 | 每换一版源码就多一份 ~400 KB 的源码副本，永不过期（本机清理前是 8 份 / 3.2 MB），而它**不能直接删**——删错一个正在跑的进程会当场 `ERR_MODULE_NOT_FOUND`。现在有认领文件 + 7 天宽限，见「engine 目录」一节 |
| 面板页在 6 秒后**无条件**宣称「面板已退出」 | 那句话是写死在 `ui/index.html` 里的**承诺**，不是观察。它与上面那条 job 空壳正好配成一对：后端卡在 `await` 上永远不退，页面却已经换成「面板已退出 / 网站与数据库已停止」——于是「页面说退了、中枢说在跑」，而两句话都是真的，只是说的不是同一件事。现在改成：整页先换成「正在停止…」并每秒画一次网站/数据库的真实状态，**等后端的响应带回真实结果**，再去探面板是否真的不再应答，探到了才说「已退出」，探不到就照实说「面板仍在运行」。见「已知限制」里那条诚实边界 |
| `taskkill` 的 `ok` 把退出码 **128** 也当成功，注释说「128 = 进程已不存在」 | 那句注释是**猜的**，而且猜反了。本机实测：128 对「不存在的 PID」「存在但没窗口、请求被拒绝」「刚被 /F 结束掉」三种情况一视同仁，不携带任何信息。于是 `stopApp` 里一次**被拒绝**的软杀被当成成功，接着 `waitForPort(…, 8000)` 白等满 8 秒（实测 8.33 秒），日志还把它记成「优雅退出超时」——像是应用退得慢，其实是这条信号在 Windows 上根本送不出去。现在 `ok` 只认退出码 0（送达），进程在不在问 `pidAlive`；送不出去就一秒都不等。实测同一条路 **9.9 秒 → 1.8 秒** |

头两条是先在本启动器上跑真实流程才暴露出来的 —— 前者靠拿真实输出对正则，
后者靠跑一次完整的七步部署；中间两条是「首次部署」失败那次的同源问题（判据合成一个、
写锁不是原子的）；再往后是写预检时踩出来的，那几条都进了「重新分配端口」的收口或
子进程环境那条线。

**前四条来自 2026-09-28 的一次真实使用**：点「全部停止并退出面板」之后，中枢仍然
显示面板运行中。四条都不是「功能缺失」，而是**判断错了**——喂出去的 job 缺方法、
留痕用的钩子没人调、删目录这件事压根没写、页面把承诺当成了观察。它们的共同点是
**外表完全正常**：界面有反馈、日志不报错（连一行都没有）、下一次启动也照常，只有
对着真实状态核对才看得出来。

**第五条是接着来的，而且是前四条之外的另一类**：用户重启之后那条路通了（日志第一次
如实写「面板退出（应用已停止，数据库已停止）」），但他去看日志时又发现一行
「优雅退出超时，改为强制终止…」——于是问「优雅退出应用是不是有问题」。有问题，
而且从前一直有：那 8 秒不是在等应用，是在等一件 Windows 不允许发生的事。它和上面表里
那条 job 空壳是同一个形状的毛病——**一个被吞掉的返回值**，只是这次吞掉它的是
`taskkill` 的 `ok`。

那次故障的排查过程本身留了一条教训，记在这里：**用户测的其实是修复前的代码。**
三条独立证据才把它钉死——`panel.mjs` 的 mtime 晚于那个面板进程的启动时间、中枢日志里
记着它是什么时候被拉起来的、`panel.log` 末尾逐字复现的是修复前的形状。用户跑的是
folder 模式（源码），所以**改了源码必须他重启中枢、并关掉重开面板才生效**；在那之前，
「我明明修好了」与「现象一模一样」可以同时为真。

## 已知限制

- **不做**（留给 v2）：把子面板的 `/api/ops/*` 与 SSE 经中枢转发，即「从中枢直接
  部署」。v1 的中枢只管列表 / 监视 / 打开 / 停止 / 校验 / 重新分配端口
- **「重新分配端口」是同步请求**：典型 10–20 秒，需要数据库崩溃恢复时可达几分钟。
  期间中枢把该项目标成 busy（卡片上有标记、按钮禁用），界面的 2 秒状态流就是进度条。
  没有引进 job 机制——那要在本功能里再塞一套 JobRegistry + 路由 + UI 订阅器
- **端口有空闲探测与实际绑定之间的 TOCTOU 窗口**：`portFree` 探完就关掉 socket，
  真正绑定在几秒（数据库可能几分钟）之后。被别的程序抢走时会明确报出**是哪一项**
  没起来，**不会**自动重试到另一个端口——那正是这套功能要消灭的那类静默换端口
- **没人能回答「谁在监听这个端口」**：全库只有连通性探测（`tcpReachable`），没有
  反查 PID 的手段，所以自动诊断有天花板，报错里给的是手工命令
  （`netstat -ano | findstr :<port>`）。由此还有一个**已知的误判**：一个从未启动过
  数据库的项目，只要它配置里的 `pgPort` 上正好有别的 postgres 在监听，`pgStatus`
  就会显示「数据库 运行中」——它把「端口有人」当成了「我的库在跑」。这是同一件事的
  另一面：分不出是谁。真要动它时（重新分配端口）保护是有效的（会拒绝并说明），
  但**卡片上的状态**在这一种情形下是错的
- **清盘（含旧部署的按名字清盘）不是原子的**：它是一串 `rmSync`，删到一半失败
  （单个文件被占在 Windows 上是常态）就会留下一个删了一半的部署。这一点靠**顺序**
  兜着而不是靠事务：先清盘、后注销，所以失败时那条项目还在列表里、重试按钮还在。
  旧部署另外多加一关：面板 / 应用 / 数据库只要有一个在跑就直接拒绝，不容忍「删一半」
- **旧部署清盘清单是新旧布局之间的一个手工约定**：`LEGACY_PURGE_RELS` 里那十几个
  名字是照着**已知的旧布局**写的。旧部署用的是哪一版 `deploy/` 决定它到底铺了哪些
  文件；清单里没有的名字不会被删，会安静地留在数据根里。删完界面上报的是**删了几项**，
  所以少删是看得见的（对不上就自己去资源管理器补），但不会自动发现
- **环境预检的自愈有边界**：它能补 PATH，补不了「一个 Node 都没有」。解析不出 Node
  （SEA 模式且运行目录里没有便携版、又没给 `--node`）时预检会判 fail 并说清要什么，
  但不会去下载一个——那件事仍在 `start.cmd` 里。另外注册表里若有引用到未定义变量的
  条目（本机真有一条 `%DevEco Studio%`，那个变量不存在），会**原样留着**：Windows
  自己也是这么做的，留着无害，只是那一条目录不可用
- **exe 内嵌的是构建机的 Node（v24.18.0）**，所以面板代码必须保持 v24 兼容。
  folder 模式仍遵守 `start.cmd` 的 `>= 20` 检查
- **`node:sea` 是可选导入**：Node 20.0–20.11 没有这个模块，folder 模式因此仍能跑；
  只有 SEA 模式要求 24+（它自带）
- blob 与注入目标必须是**同一个 Node 版本**，换 Node 之后要重新打包
- **页面说「已退出」现在是观察，但它有一个诚实的边界**：点「全部停止并退出面板」之后，
  页面不再定时宣告，而是等后端把**真实结果**（应用停没停、数据库停没停）写进响应，
  再逐秒探 `/api/state`，**探不到对端才说「面板已退出」**。三种收尾都写清楚了：
  探到退出 + 有结果 → 逐条说明停没停；探到退出 + 响应断在半路 → 「面板已退出」但
  **「停止结果没能确认，请到中枢里核对」**；15 秒内仍探得到 → **「面板仍在运行」**，
  并把已拿到的结果一并列出。中间那条就是边界：**响应丢在半路时页面无从知道结果**，
  它只能说没拿到，不能替后端宣布成功。后端那边还有 120 秒硬超时兜底，到点时它会退出，
  日志照实写「停止动作在 N 秒内没有结束……应用或数据库可能仍在运行，请到中枢里核对」
- **Windows 上没有「优雅地停止应用」这条路，应用只会被强制终止**：不带 `/F` 的
  `taskkill` 只给目标进程的**顶层窗口**发 WM_CLOSE，而应用是 detached + windowsHide
  起的——它**没有窗口**，于是 taskkill 当场拒绝执行、进程一动不动。这不是本启动器能绕
  过去的：没有窗口的进程只会收到「被结束」，收不到「请结束」；唯一的替代（给它配一个
  隐藏控制台再发 CTRL_BREAK）要用到 Node 给不了的原生调用，而且会破坏「关掉面板应用
  照跑」那条保证。所以现在的做法是**如实**：一秒都不空等，日志写清「应用没有窗口，
  Windows 送不出关闭请求」。代价是应用的在途请求会被切断——本地部署面板上这是可接受的，
  但**别把「停止应用」当成一次 graceful shutdown**
- **旧标签页的令牌会失效**：面板令牌每次启动随机生成。面板重启**之前**打开的那个
  标签页，其后所有改动型请求都会 403。以前这种事在日志里不留痕（连一行都没有），
  现在会留一行并提示「刷新页面即可」，但**页面本身只显示一句失败** —— 得你自己想到
  去刷新。这不是能靠文案解决的事：页面拿不到新令牌，除非重新加载它
- **engine 里那 7 份历史副本是手工清掉的，不是判据自己完成的**：判据只能靠认领文件
  生效，而那批目录是**认领机制之前**释放的（都没有 `.inuse`），按 7 天宽限它们本来
  还会留着。所以那是一次取证之后的**一次性**清理（先确认三个活进程的命令行里都不含
  `engine\`），而它顺带证明了这条宽限是必要的——如果没有它，清理逻辑一上线就得在
  「删掉一个可能还在跑的进程」和「一份都删不掉」之间二选一

运行期：

```
%LOCALAPPDATA%\AgileCampus\
├─ projects.json              注册表
├─ config\hub.secret          监督令牌
├─ engine\<内容哈希>\          从 exe 释放的源码（同版本重复启动零写入）
│                              .inuse = 认领文件，正常退出时自动抹掉；旧的会自动清理
└─ projects\<slug>\           每个项目：config src node pgsql pgdata logs run tmp
```

`<slug>` = `kebab(仓库目录名)` + `-` + `sha1(绝对路径).slice(0,8)`。加路径哈希是为了
**同一项目的两份检出不会互相覆盖** —— 基名相同、路径不同的两个目录必须落在
不同的运行目录里，否则 B 的 `npm ci` 会覆盖 A 的 `node_modules`、
B 的 `drizzle push` 会打进 A 的库。

**例外：被收编的旧部署没有 `projects\<slug>\`**，它的运行目录就是上面那个数据根本身，
`src node pgsql pgdata logs run tmp` 直接长在 `config\hub.secret` 旁边。所以它的
`config\panel.json` 与 `run\hub.lock`、`logs\hub.log` 是**同一层里的不同文件**，
清盘只能按名字做（见上文「已有的旧部署会被原地收编」）。

## 打包

```bat
npm i -D postject      :: 唯一的开发依赖
node build\build-sea.mjs
```

流水线四步，**不需要 esbuild**：面板源码以 ESM 原样内嵌，由 `boot.cjs` 释放后再
`import()`。被编译成 CJS 的只有 `boot.cjs` 自己，而它是手写的 CJS。

两个必须记住的坑：

- SEA 配置里 `useCodeCache` **必须是 `false`**。Node 文档明写
  "import() does not work when useCodeCache is true"，而 `boot.cjs` 的全部工作
  就是 `import()` 释放出来的 `main.mjs`
- `--macho-segment-name` **只在 macOS 需要**，win32 传了反而出错

打包前会跑一遍 `verify-ui.mjs` 检查每个 HTML —— 界面坏了就不该被打进 exe。

还会跑 `verify-ports.mjs` 的**纯检查**：它守的是「端口组 + DSN + .env」这条不变式，
横跨三个文件，而它漂移起来是静默的（界面一片正常，只有应用连不上库时才发作）。
纯层不碰网络也不碰磁盘，所以在任何构建机上都能跑；它的文件层
（`node verify-ports.mjs --data-root <数据根>`）需要一份真实部署，只由人手动跑。

还会跑 `verify-childenv.mjs`：它守的是「交给子进程的环境里 node 一定跑得起来」。
`{ ...process.env }` 是**普通对象**，而 Windows 上 PATH 的键名是 `Path`（注册表就这么
写的），所以 `env.PATH = ...` 里的 `env.PATH` 读到 `undefined` —— 整条继承来的 PATH
被替换成只剩 pgsql 的 bin，npm 的 postinstall 里五处裸 `node`（esbuild ×3、sharp、
msw、unrs-resolver）全部报「'node' 不是内部或外部命令」，「首次部署」卡在 npm ci。
**这个 bug 从 git-bash 启动时永远复现不了**（MSYS 把键名设成大写的 `PATH`），只有
Explorer / `cmd.exe` 起的才中招，所以它必须自己构造两种大小写来测，并且真的起一个
cmd.exe 跑 `node -v`（外加一条「修复前的写法确实会失败」的反证，否则分不清这个测试
是在测东西还是碰巧通过）。

还会跑 `verify-panelstate.mjs` 和 `verify-preflight.mjs`，它们各自守一条**曾经搞错过的
判断**：

- **「面板在不在」与「面板答不答话」是两个问题。** 判据曾经合成一个（锁 + pid 存活 +
  1.5 秒内应答 `/api/state`），于是中枢每 2 秒轮询一次就有机会把「忙」误报成「没开」：
  卡片闪一下「面板：未打开」，详情里还谎报「锁陈旧（进程已不在）」，点「打开控制面板」
  会去起第二个面板而端口被第一个占着。而面板是单线程的，跑 npm ci / 构建时 1.5 秒不
  回话是**常态**。现在 `panelProcess`（锁 + pid）管「在不在」，`livePanel`（+ 应答）只用
  在「马上要拿它的结果去用」的地方。这个验证器起一个**真的只监听、永不应答**的进程来
  当那只忙碌的面板，所以它验的是真事；那之后中枢里问「在不在」的地方一律看进程
  （含「重新分配端口」的预检：问不到面板在忙什么就拒绝，绝不把正在跑 npm ci 的面板停掉）
- **部署用的那份子进程环境坏了自己会补回来。** `withPath` 管得住「node 与 pgsql 在不在
  PATH 上」，管不住「继承来的那一段本身是不是坏的」——缺了 `System32`，npm 在 Windows 上
  连 `cmd.exe` 都起不来（它就是靠 cmd.exe 跑 postinstall 的），而报出来的错指向别处。
  所以 `lib/preflight.mjs` 会在缺系统目录时从**注册表**读一份「机器 + 用户」PATH 补上
  （**只增不减**，不可能把本来能用的弄坏），并注明「补了什么、为什么」——静默自愈是另一种
  撒谎。同一批检查还做两件事：在 `deployAll` / `rebuildAll` 开跑前真起一个 `cmd.exe`
  跑 `node -v`（不过就带着准确的原因停在 npm ci 之前，**不重试**——重试只会把「环境坏了」
  藏得更深），以及进「检修」（`FIXES['env-path']` 排在第一，因为环境坏了的话后面那些
  修复项自己也会起不来）。验证器里最有说服力的两条是真跑出来的：把环境弄坏 →
  `cmd.exe /c node -v` 必须失败（反证），同一份坏环境走一遍 `buildEnv` → 必须能跑起来。

还会跑 `verify-legacypurge.mjs`。它守的那条不变式**错起来是不可逆的**：旧部署的清盘
清单一共十几条相对路径，写成 `logs` 而不是 `logs\app.log`，用户点一下「删除并清盘」，
中枢自己的 `hub.log` / `hub.lock` / `projects.json` / `engine/` 就没了——而且现场一声
不响，因为注册表正是被删掉的第一个文件，下一次启动得到的是一份全新的空注册表，看起来
像「用户从没加过项目」。验证器在一个临时目录里造出「数据根里长着一套旧部署、中枢自己
也在用这个目录、另一个项目的运行目录还长在里面」的现场，然后断言删完之后**每一件该留
的东西都还在**。两条反证各自守一种「测试其实没测到东西」：普通项目走同一条路必须真的
把整个目录删掉（否则那串「还在」只能证明这个函数是个空操作），以及移出列表之后
`migrateLegacy` 必须**不再**收编（不先证明「没有那一笔时它确实会被收编」，那句 `false`
就分不清是修好了还是压根没走到）。纯磁盘操作，不碰网络也不碰用户的数据根。

`node verify-legacypurge.mjs --e2e` **进不了门禁，也不必进**：它自起一个临时中枢
（临时数据根、随机端口，跑完自清），把整条 HTTP 路径走一遍——确认短语错了是 400、
数据库端口上有人时是 409 且磁盘一字未动、清盘后重启中枢它不会自己回来、「添加项目」
把它加回来会撤销那一笔。不进流水线是因为它要起进程、占端口。它第一次跑就抓到一个
**真 bug**：界面的「移出列表」发的是不带 body 的 `DELETE`，而护栏对 `/api/` 下所有
非 GET 都要求 `application/json`（哪怕没有 body），于是那个按钮一直是 415——只有一条
红字，什么都不发生。这个坑正好在旧部署身上最要命：那是它唯一一条不清盘的退路。

那一段里还有一个**测试自身的**坑，值得记下来：`run\hub.lock` 是在 `server.listen`
**之后**才写的，中间夹着一次 ~1–2 秒的 `processStartTime`（PowerShell）。HTTP 已经
能应答、锁还没落盘，这时候下断言就会看到「中枢在跑但锁没写」——一个根本不存在的
故障。所以「就绪」必须是**两件事都成立**，而且令牌每次启动都换，重启后必须重读。

还会跑 `verify-engine.mjs`。清理 engine 目录本身很容易，难的是**分清「有进程正在用」
和「没人要的旧副本」**（理由见「engine 目录」一节），所以判据里每一条「宁可留着」的
理由都得有用例钉着，外加一条「`engine\` 之外的邻居一字未动」。它另外钉住两件事：
`require('boot.cjs')` 必须什么都不做（那个文件只能在 exe 里启动），以及调用顺序必须是
**先认领、再清理**——顺序反了就会把自己的目录当成无人认领的（断言里找的是**调用点**
字符串而不是函数名，否则永远会匹配到定义、永远通过）。在系统临时目录里跑，不碰你的
数据根。

还会跑 `verify-shutdown.mjs`，它守「退出面板」这条路以及「护栏的拒绝必须留痕」。
最有说服力的一段是**反证**：先把一个手写的 job 空壳喂给 `stopPortable`，断言
`job.flush is not a function` 真的被抛出来、并且 3 秒内不 settle（面板因此永不退出——
这正是那天故障的机理）；再换成真 `detachedJob`，断言一定 settle 而且很快。没有这段
反证，这个验证器就分不清「修好了」和「压根没走到那段」。它还在全仓库扫一遍不许再出现
第二种手写的 job 空壳，而那个扫描正则**自己也有一条反证**（证明它在修复前的写法上
确实命中）。它刻意不造 `pg_ctl`：spawn 直接 ENOENT，正好走到 `'error'` → `done()` →
`job.flush()` 那条要测的路上。

它还有一段专测**停止应用不再空等**，而那里的反证是**真去问一次 Windows**：起两个
headless 的哑进程（形状甲 detached + windowsHide，就是应用的样子；形状乙只有
windowsHide），对它们各跑一次不带 `/F` 的 `taskkill`，断言**都被拒绝、进程都还活着**，
再对一个不存在的 PID 跑一次，断言拿到的也是非 0 —— 于是「退出码区分不了『被拒绝』与
『不存在』」不再是我的说法，而是当场可复现的事实。不这么测就拦不住一件事：将来有人
把「等 8 秒」加回去，现象只是慢 8 秒，小到不会被报上来。两种形状都要测，是因为它们
**退出码不一样**（本机实测 255 与 128），而老代码恰好只把 128 当成了成功。

`node verify-shutdown.mjs --e2e` **进不了门禁，但它是唯一能证明那条路真的修好的测试**，
所以别省掉。上面那一整层（静态断言 + 反证）只证明「真 Job 会 settle」，而用户报的是
**这一层**：应用和数据库都在跑的时候点下去，三样（应用、数据库、面板）到底停没停。
于是它真的起一套：在系统临时目录里 `initdb` 出一个数据簇、`startPortable` 起一个真库、
起一个哑 node 进程占住 appPort 并用 `recordStarted` 登记成「应用」，然后起一个**真面板**
（就 `node main.mjs`，带 `--repo` / `--runtime-dir`），从页面里取令牌，
`POST /api/ops/shutdown {alsoStopApp:true, alsoStopDb:true}`，再断言：响应带回了
`stoppedApp === true && stoppedDb === true && errors.length === 0`、面板进程**真的退出**、
两个端口都不再有人监听、`panel.lock` 被清掉、`app.json`/`pg.json` 都被置空、
`pgdata\PG_VERSION` 还在（停的是进程，不是数据）、而 `panel.log` 里那句话与事实相符
（不再无条件写「应用与数据库继续运行」）。它另外钉住「停止应用不再空等那 8 秒」——
那个哑应用是 headless 起的，必然走「Windows 送不出关闭请求」那条路，所以日志里
**不许再出现「优雅退出超时」**，而整轮停止必须明显短于那 8 秒（实测 **9.9 秒 → 1.8 秒**）。

两处要留神：**端口全部现挑**（这台机器上真的跑着用户的部署，写死配置默认值就是撞车）；
`pgsql\` 用的是**目录联接**指向用户那套二进制（只执行、不写入，`pgdata` 落在临时目录），
收场时必须先用 `cmd /c rmdir` 摘链接、**绝不能用递归删除**——万一联接被当成普通目录
走下去，删掉的就是用户那套 886 MB 的二进制。所以它删完还要**回头断言那份二进制一个
字节没少**，并且真的打印出来。

`node verify-realloc.mjs` **进不了门禁，也不必进**：它自己起一个临时中枢和两个临时
面板（都在系统临时目录里，端口现挑，跑完自己收场），全程约一分半。它不碰你的数据根，
也不碰任何已在运行的进程。不进流水线是因为它要起进程、占端口，像测试多过像门禁；
不删掉是因为**纯函数测不到它测的那一层**——「重新分配端口」的正确性几乎全在跨文件的
写顺序上（`panel.json` 三个端口、由 `pgPort` 派生的 `databaseUrl`、`.env` 的
`DATABASE_URL` 与 `AGILECAMPUS_URL`，四处必须一起改对），还有「拒绝的时候磁盘是否
真的一字未改」。这个功能**真的在那一层出过 bug**：`allocatePorts` 的 `avoid` 参数原先
写成「把自己当前的端口从预约集合里去掉」，于是中枢把原样三个值当成建议值发回来，
界面一切正常、点了等于没点；当时 `verify-ports.mjs` 那条用例也照着错语义写，两边一起
错，只有真跑一遍才看得见。它同时也验面板那两个「也能改端口」的写点是否收口
（`AC_HUB=1` 时严格、独立运行照旧）——那两条只在面板进程里，中枢侧的测试看不到。

中枢页额外跑一遍 `verify-hub-render.mjs`：它把 `hub-ui/index.html` 里的脚本放进一个
带最小 DOM 桩的 `vm` 里，**真的执行 `render()`**（用真实形状的载荷，可选 `--live`
直接喂运行中的中枢返回的那份）。这是必要的补充而不是重复，因为 `verify-ui.mjs` 只数
`report()` 的调用点，看不懂一个属性读的是谁 —— 中枢页曾经写成 `h.projects.length`
（`hub` 对象根本没有这个字段），`render()` 第 5 行就抛，**它后面每一行画卡片的代码
都从没执行过**，而静态检查对此一言不发。一个从没跑过的渲染路径，和一条跑起来是对的
渲染路径，在外表上完全一样。
